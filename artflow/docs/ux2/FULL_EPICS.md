# [UX2] Программа редизайна Mini App: эпики, последовательность и доказательства выпуска

Source: https://github.com/Bambale0/lena_bot/issues/209

## Цель
Довести утверждённый UX/UI 2.0 Telegram Mini App APIX от админского предпросмотра до понятного, безопасного и проверенного продукта. Пользователь выбирает действие, видит материалы и цену, контролирует запуск и находит результат без помощи разработчика.

## Подтверждённая база
PR #208 выпущен: `d97184f4a9587a8237df6504de1fe58ff8142c22`. Есть пять разделов в admin opt-in preview, экран создания, библиотека работ и session-черновики. Это фундамент, а не завершённый редизайн. Источник предыдущих доказательств: #208, комментарий 6087220264.

## Границы
Перерабатываем только Mini App. Не делаем лендинг, не меняем визуал отдельного сайта и текстового бота. Общие API, права, тарифы и финансовые правила сохраняют совместимость. Без новых выдуманных моделей, подписки PRO, процентов генерации, обещанного ETA или неподтверждённых кнопок отмены. Скрытые промпты и встроенные авторские материалы не отправляются клиенту.

## Порядок исполнения и статусы
Одновременно в работе один проверяемый вертикальный срез. Порядок: E01 материалы → E02 редактор → E03 повторы → E04 жизненный цикл → E05 результаты → E06 навигация и поиск → E07 баланс/профиль → E08 WebView/доступность → E09 контроль возможностей и диагностика → E10 пилот. Это порядок выполнения, а не искусственная зависимость всех эпиков друг от друга. Точные блокирующие результаты указаны в каждом эпике; подготовка E08/E09 допускается раньше, но не расширяет текущий scope.

Статусы: `backlog → ready → in_progress → verification → pilot_verified → released`. Закрытие PR не закрывает родительский эпик, пока не пройдены все критерии эпика. Открытый deployment или наличие мок-тестов не считается production verification. Пропущенные проверки указываются явно.

## Обязательный контракт каждого среза
1. Уточнить актуальный SHA и инструкции; сверить существующие API/схемы/тесты и риск соседних изменений.
2. Зафиксировать пользовательское поведение и acceptance tests, воспроизвести RED.
3. Сделать минимальную реализацию; не стирать введённое, не отправлять лишние данные, не ослаблять авторизацию.
4. Проверить unit/контракты/браузер, негативные случаи, reload/back/ошибки сети. Приложить команды и результаты, screenshots для UI.
5. Review: требования, безопасность, конфигурация, telemetry, влияние на сайт/бот.
6. PR → необходимые checks на точный SHA → штатный автодеплой → health, asset SHA и стартовые логи. Никаких push в main или manual checkout production.
7. Обновить активную задачу, эпик и execution ledger. Только затем перейти к следующему срезу.

## Шаблон доказательства
`task_id / base_sha / head_sha / PR / RED / GREEN / screenshots / API-contract checks / admin-preview status / deployment_sha / health / not_verified / rollback`.

## Релизные ограничения
Сохраняем существующий admin opt-in до отдельного прохождения E10. Проверка readonly production не даёт права на платные пробные запросы, массовые рассылки, изменения балансов или разрушительные миграции. Для реальных оплат и генераций сначала ограниченный явный тестовый бюджет и подтверждённый сценарий.

## Успех программы
Все три пути работают: идея → генерация; пример → повтор; задача → результат. Нет потери материалов и повторных списаний; пользователь понимает обязательные входы, стоимость, статус и следующий шаг. Сравнение удобства проводится с измеренным baseline на пользовательских тестах, а не с обещанием роста конверсии.

## Текущий срез
E01.1: неразрушающая смена модели/режима обычной генерации, видимость несовместимых материалов, блокировка некорректного запуска. Полноценное активное/отложенное использование файлов и долговременное хранение — отдельные срезы E01.

# [UX2-E01] Материалы и черновики без потери данных

Source: https://github.com/Bambale0/lena_bot/issues/210

## Родитель и цель
Программа #209. Пользователь свободно меняет модель, режим и экран; его фото, видео, описание и параметры не исчезают. До запуска видно, что будет использовано и что требует исправления.

Приоритет P1. E01.1 готов к выполнению после #208. Остальные срезы запускаются после указанных ниже результатов, а не после формального закрытия всего эпика.

## База и границы
В PR #208 есть owner-scoped sessionStorage обычных черновиков. Смена модели и режима ещё очищает массивы. Состояние дополнительных Seedance-референсов частично живёт в DOM enhancer: оно не считается покрытым сохранением React GenerationDraft. Нужна явная инвентаризация всех источников материалов. Не переписываем адаптеры провайдеров и не переносим скрытые данные трендов на клиент.

## Вертикальные срезы
- [ ] **E01.1 — неразрушающее переключение обычной генерации.** Смена модели/режима сохраняет исходный набор медиа и совместимые параметры. Несовместимые входы видны с причиной. В первой версии запуск блокируется до решения пользователя, а не молча урезает массив. Повторный переход к исходной модели возвращает тот же набор. Результат проверяется в DOM, storage и перехваченном POST.
- [ ] **E01.2 — активные и отложенные материалы.** После E01.1 пользователь может явно исключить файл из текущего запуска без удаления из черновика. Никакого автоматического выбора «первых N» при уменьшении лимита. Сборщик payload включает только выбранные активные входы; стоимость считается для того же снимка. Источник правды один, UI не хранит второй независимый список.
- [ ] **E01.3 — наглядная загрузка.** Превью, просмотр оригинала, имя/тип/размер и роль файла, повтор неудачной загрузки, удаление, замена. При частичном провале серии успешные загрузки не исчезают. Пока upload не завершён, нельзя запустить задачу или применить переключение к другому черновику. Поздний ответ не воскресает после явного удаления.
- [ ] **E01.4 — устойчивые ссылки.** Сначала проверить существующие asset IDs/ownership/TTL. Сохранять долговременный идентификатор, а не обещать бессрочность внешнего URL. При 403/404/истёкшей подписи получить новый разрешённый URL либо попросить повторную загрузку, сохранив описание. Не выполнять клиентские запросы к произвольным приватным сетям; серверный resolver валидирует URL и владельца.
- [ ] **E01.5 — версии черновиков и восстановление.** После E01.2–E01.4: явный draft ID, версия схемы, пользователь, источник сценария, время. Версионируемая миграция без раскрытия старых скрытых полей; обработка corrupt/quota/private-mode. Между аккаунтами нет восстановления. Между устройствами — только через разрешённый серверный контракт, не через перенос initData.
- [ ] **E01.6 — унификация дополнительных входов.** После инвентаризации заменить side-state enhancer для Seedance video/audio/role refs на типизированный черновик с контрактными тестами. Переносить по одному провайдерскому пути, временно сохраняя legacy adapter. Один формат mediatype/role не предполагается универсальным без проверки.

## Критерии приёмки эпика
- [ ] A→B→A сохраняет порядок и полный набор фото; видео и trim не исчезают.
- [ ] Лимит 4→1 не удаляет три фото и не создаёт платный запрос без явного решения.
- [ ] Неподдерживаемые photo/video/audio/character inputs не попадают в POST.
- [ ] Переключение во время upload имеет детерминированное поведение, не привязывает файл к чужому аккаунту или черновику.
- [ ] Reload/back/оплата/ошибка сети сохраняют обычную подготовку; ограничения хранения сообщаются честно.
- [ ] Удаление означает удаление, исключение из запуска означает сохранение; подписи различимы.
- [ ] ModelInfo является источником лимитов; никаких новых захардкоженных ID, тарифов или provider limits.
- [ ] Скрытые prompt/template assets отсутствуют в DOM, local/session storage и телеметрии.

## Проверки и диагностика
Unit: immutable transitions, A/B round-trip, modes, explicit zero/unknown limits, metadata skew, duplicate URLs, seed/IDs. Browser: два совместимых/несовместимых фиктивных провайдера, delayed upload, double-click, reload, account switch, 320px, light/dark. Контракт: UI и submit используют одинаковый compatibility result, отрицательный сценарий имеет 0 generation POST. Для новых событий — только draft correlation, action, counts и reason codes; не URL и не описание. Любая P0 утечка/двойное списание блокирует выпуск.

## Выпуск и откат
Только admin preview; старый UI/повторы трендов не меняются до своего среза. Каждый срез — отдельный PR с RED/GREEN, screenshot, точным SHA и production verification. E01.1 не закрывает E01. Долговременное хранение, cross-device и enhancer migration остаются открыты, пока не проверены отдельно.

# [UX2-E02] Единый редактор: понятные сценарии, основные и расширенные настройки

Source: https://github.com/Bambale0/lena_bot/issues/211

## Родитель, цель, зависимости
Программа #209. Пользователь создаёт фото или видео в одном понятном редакторе, без обязательного шестишагового мастера и изучения provider-терминов. Приоритет P1. E02.1 опирается на #208 и неразрушающий черновик E01.1 (#210); подключение ролей материалов — на E01.2/E01.3. Полный E01 не является блокером простого редактора.

## Продуктовые решения
Основные действия: создать/изменить фото, оживить фото, создать видео, перенести движение, изменить видео — только при реально поддерживаемом контракте. «Рекомендуемая» модель видна по имени и доступна для замены; нельзя автоматически менять качество/провайдера/цену за пользователя. Быстрый выбор модели остаётся у профессионалов. Бизнес-правила и параметры берутся из backend metadata.

## Вертикальные срезы
- [ ] **E02.1 — фото от идеи до результата.** На одной странице материалы, «Что хотите получить», компактная модель, формат/качество и цена. Начальные пустые поля не окрашены красным; после попытки запуска ошибка рядом с полем и фокус на первом препятствии. Обязательные поля отмечены явно. Существующий image POST и task sheet переиспользуются.
- [ ] **E02.2 — два уровня сложности.** «Основные / Расширенные» редактируют один draft. Seed, несколько запусков, character/audio IDs и provider-specific controls скрыты в advanced, но выбранные нестандартные параметры отражены в краткой сводке. Переключение уровня не сбрасывает ничего. Основной режим делает один платный запуск; количество результатов не называется количеством задач.
- [ ] **E02.3 — видео и движение.** Один редактор с секциями по выбранному сценарию, ролью исходного ролика, форматом и длительностью. «Изменить это видео», «Создать по референсу» и «Перенести движение» не имеют одинаковых payload по умолчанию. Для source-duration стоимость пересчитывается из разрешённого измерения; неизвестная длительность не заменяется выдуманным числом.
- [ ] **E02.4 — выбор модели.** Поиск и сравнение доступных моделей по проверенным возможностям, цене и требованиям. Недоступная модель не исчезает из черновика молча: объяснение, смена вручную. Каталог и фильтры используют тот же capability contract, что форма и API. Не добавляем AI-рекомендацию, автоматически выбирающую дорогую модель.
- [ ] **E02.5 — единая панель запуска.** Действие «Создать за {стоимость} {валюта}» остаётся видно без перекрытия поля клавиатурой. При недостатке средств — сохранённый переход в оплату, а не тупик. Окончательная сумма и model snapshot согласованы с сервером (E07). Таймаут не превращается в повторный платный POST (E04).
- [ ] **E02.6 — редактирование текста и возвраты.** Сохранение описания, расширенных настроек и scroll/focus при просмотре фото, выборе модели, истории и Back. Подсказки описывают ожидаемый результат человеческим языком. RU/EN тексты централизованы; термин «референс» объясняется назначением, а не маркетинговым слоганом.

## Критерии приёмки
- [ ] Фото можно подготовить и отправить без открытия advanced; нет обязательного лишнего wizard.
- [ ] В DOM один владелец draft и одна основная submit-команда.
- [ ] Все параметры активной модели доступны в подходящем уровне; ни один разрешённый capability не потерян.
- [ ] Условия обязательности медиа/промпта одинаковы в UI и API.
- [ ] Count=результаты и taskCount=запуски явно различимы, общая сумма соответствует обоим.
- [ ] Сворачивать advanced безопасно: выбранные значения сохраняются.
- [ ] Недоступность каталога, отключение модели, изменившаяся цена и частичная ошибка upload имеют восстанавливаемое состояние.
- [ ] Никаких «100% готово» и обещаний ETA, не полученных от сервиса.

## Тестовый пакет
Playwright: text→image, image→image, text→video, image→video, motion, metadata change, no models, 0 balance, duplicated click, keyboard-size viewport, long prompt, 200% text, two language/theme combinations. Captured payload должен точно соответствовать показанным сводке/материалам. Проверить существующие 300 journeys без изменения их финансового смысла. Для каждого нового сценария — positive и negative contract tests плюс screenshot до/после.

## Технические границы и observability
Не переписываем App целиком: выделять pure selectors/reducer/components по мере нужды, сохранять существующий API client. Model choice не дублируется в CSS/enhancer. Метрики: editor_open, scenario_selected, validation_blocked(reason), submit_requested, task_accepted; отделить UX time-to-submit от provider latency. Не логировать промпты, фото и initData. Выпуск малыми admin-preview PR, откат штатным revert; широкое включение только E10.

# [UX2-E03] Тренды и повторы: единый понятный путь без раскрытия авторских данных

Source: https://github.com/Bambale0/lena_bot/issues/212

## Родитель, цель, зависимости
Программа #209. Пользователь открывает пример, понимает нужные исходники, заменяет только разрешённые поля и явно подтверждает платный повтор. Приоритет P1. Первый срез доступен после baseline #208; общий uploader зависит от E01.2/E01.3 (#210), общая оболочка редактора — E02.1 (#211). Не блокировать каталог ожиданием долговременного draft backend.

## Границы
Лента и каталог трендов — разные точки входа, но одинаковая операция не должна давать разные правила. Общие UI-компоненты можно переиспользовать; серверные feed-remix и trend-run контракты не объединять насильно. Скрытый промпт, встроенные референсы и авторские права остаются на backend. Подготовка/загрузка/открытие ссылки не списывают средства.

## Вертикальные срезы
- [ ] **E03.1 — карточка до запуска.** Крупный пример, название, понятный эффект, тип/число требуемых пользовательских материалов, разрешённые изменения, цена или честный диапазон. Требования получаются для конкретного шаблона, не общим текстом «одно фото». Устаревший/удалённый шаблон имеет безопасное объяснение и возврат в каталог.
- [ ] **E03.2 — повтор с моими материалами.** У каждого слота роль, required/optional, лимит и инструкция. Встроенное исходное видео не надо загружать повторно. Авторские скрытые входы не превращаются в пользовательские URL. При добавлении фото показывать готовность к запуску, но не запускать автоматически. Два обязательных слота нельзя перепутать порядком массива.
- [ ] **E03.3 — редактируемые значения шаблона.** Возраст/имя/надпись/число/дата/одежда только из разрешённой схемы. Валидация длины, типа, диапазона и Unicode на сервере; UI показывает тот же смысл. Изменения пользователя не подменяют скрытый промпт и не могут добавить произвольные provider fields.
- [ ] **E03.4 — фото + исходное видео.** Разделить source-edit, reference-generation и motion. Выбранный сценарий и роли должны быть проверены в route→validator→adapter. Для замены персонажа отдельный contract/smoke с допустимыми материалами; не обещать точность идентичности, пока она не проверена. Не расширять оплачиваемые тесты без отдельного разрешения.
- [ ] **E03.5 — возврат из оплаты и повторное открытие.** Сохраняются выбранные фото/формат/поле шаблона и pending invoice. Проверять именно тот платёж, не произвольный рост баланса. Закрытие, reload, задержанный webhook и возвращение по старой ссылке не создают вторую оплату или генерацию. Использовать уже защищённый путь PR207/208.
- [ ] **E03.6 — публикация и предпросмотр администратором.** Перед публикацией шаблон проходит тот же пользовательский runner без admin-only обходов. Preview видит только разрешённые роли и поля. Отдельная публикация не меняет права существующих работ; версия шаблона фиксируется для уже подготовленного запуска либо требует повторного подтверждения.

## Приёмка
- [ ] По карточке понятны входы и ожидаемый эффект без открытия справки.
- [ ] Нет автоматического платного запуска при upload или deep link.
- [ ] Одна операция из feed/trends даёт согласованные поля, цены и ошибки.
- [ ] Внутренние материалы не требуются у пользователя и не утекли в JSON/DOM/storage.
- [ ] Неизвестное поле и превышение лимита отвергаются сервером до списания.
- [ ] Удалённая модель/шаблон и старый quote восстанавливаются без потери пользовательских файлов.
- [ ] Опубликованный шаблон проверен обычной ролью, не только его автором.

## Проверки
Unit/contract: source ownership, template version, hidden prompt, interpolation limits, reference slot accounting, aspect ratio and source duration. Playwright: feed→repeat, trends→repeat, ref/deep link, required two photos, optional photo, low balance, invoice reuse, stale template, cancel/Back, long title. Негативные API-тесты: чужой/private источник, invalid asset signature, удалённый trend, admin impersonation, неизвестные поля. # [UX2-E04] Запуск, ожидание, восстановление и доставка результата

## Цель и зависимости
Программа #209. Пользователь понимает, принят ли запуск, где задача, можно ли закрыть Mini App и как получить готовое. Приоритет P0 для повторных списаний/утраты результата, P1 для остальных состояний. Базовый аудит доступен сразу после #208; привязка draft snapshot зависит от E01 (#210), новый submit UI — E02 (#211).

## Границы
Разделить три состояния: создание задачи, состояние провайдера, доставка результата. `reconciliation_required` не означает ни отказ, ни обычную очередь, ни возврат средств. UI не обходит серверную admission protection. Проценты/ETA показываются только при реальных данных, отмена — только при подтверждённой поддержке.

## Вертикальные срезы
- [ ] **E04.1 — подтверждённый запуск.** До POST фиксируются выбранная модель, параметры, медиа и согласованная цена. Двойной клик, rerender и повторный callback используют одну операцию/idempotency policy. При потере ответа клиент ищет результат исходной операции, а не автоматически отправляет новую платную задачу. Сначала проверить существующие идентификаторы и storage, не создать параллельный источник истины.
- [ ] **E04.2 — карточка активной задачи.** На экране создания и в Работах доступен переход к актуальному статусу. Текст: отправляем/в очереди/создаётся/уточняем/готово/ошибка; неизвестный backend status получает безопасное описание, не raw enum. Видны время старта, прошедшее время и код поддержки. Обновить статус — отдельное read-only действие.
- [ ] **E04.3 — realtime и reconciliation.** WebSocket reconnect с bounded backoff; polling fallback не размножается при смене вкладок. Stale ответ не понижает terminal status, duplicate/out-of-order events дедуплицируются. Resume после сна/офлайна получает актуальную задачу по владельцу. Прерванный fetch не показывается как ошибка генерации.
- [ ] **E04.4 — доставка в Telegram.** Готовый результат доступен в приложении независимо от возможности чата. Отдельно проверить chat permission/write access и отправку. «Доставлено» появляется только после подтверждённого send; иначе понятный CTA открыть/подключить бот. Повторная доставка не запускает генерацию и не списывает ещё раз; message deduplication обязательна.
- [ ] **E04.5 — ошибки с действием.** Invalid input, content rejection, upstream outage, timeout, unknown admission, expired media, download failure различаются. Повтор загрузки, проверка статуса, исправление данных и новый платный запуск не называются одной кнопкой «Повторить». Финансовый текст берётся из ledger/settlement, не из локального предположения.
- [ ] **E04.6 — несколько результатов/частичные запуски.** Пакет имеет список дочерних задач и реальное число принятых. После частичного успеха пользователь видит готовые/ожидающие, не получает сообщение «всё не удалось». Повторяется только явно выбранная незапущенная часть; uncertain child нельзя переотправлять вслепую.

## Приёмка
- [ ] У каждой принятой задачи стабильный идентификатор и путь восстановления после reload.
- [ ] Не более одного списания на логическую операцию; unknown response не делает второй POST.
- [ ] Готовая работа видна без Telegram-чата; доставка отражена отдельно.
- [ ] Нельзя получить чужую задачу по ID или чужой receipt.
- [ ] Никаких фиктивных процентов, возвратов, отмены или сроков.
- [ ] Нет дублирующихся таймеров/сокетов после десятков переключений.
- [ ] Каждая ошибка предлагает допустимое действие без потери draft.

Domain/API: concurrent submissions, duplicate idempotency key, request timeout after admission, out-of-order webhook, duplicate delivery, stale completed→pending, unauthorized task lookup, partial batch failure. Browser: offline/reconnect, close/reopen, low balance, hidden app, missing chat, inaccessible media, stale socket. Исходный сценарий проверять по request_id→task_id→provider_id→ledger→delivery_id, а не только зелёному CI.

## Observability и выпуск
Минимальные поля: actor scope, task/request ID, model/provider, stage, duration, retries, result/delivery outcome. Метрики не публикуют prompts/media URLs. Алерты/таймауты управляемы существующим control plane. Если нужны schema changes — отдельный expand/contract PR с совместимостью и reconciliation. Admin preview не отменяет backend parity для сайта/бота. При регрессии денег остановить новые запуски затронутого маршрута штатным механизмом, а не вручную править balances.

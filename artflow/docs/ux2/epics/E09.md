# [UX2-E09] Единый контракт возможностей, управляемая конфигурация и наблюдаемость

Source: https://github.com/Bambale0/lena_bot/issues/218

## Цель и зависимости
Программа #209. Интерфейс, серверная валидация и provider adapter согласованы: доступны только реальные операции, лимиты/цены меняются в одном месте, каждый сбой можно проследить до причины. Приоритет P1/P0 для несогласованного списания или утечки. Инвентаризация начинается сразу; миграции делаются по срезам E01–E07, не отдельным переписыванием всего backend.

## Вертикальные срезы
- [ ] **E09.1 — карта фактических контрактов.** Для image/video/motion/music/assistant и трендов описать runtime source, fields, modes, role rules, max refs включая совместные квоты, pricing и available flags. Отделить существующие поля от предложенных. Проверить DOM enhancers, legacy adapters, web и bot; один отсутствующий capability не считать поддержанным по названию модели.
- [ ] **E09.2 — типизированные возможности.** Schema/DTO валидируется на входе клиента и сервера, null/0/missing не взаимозаменяемы. `max_refs=0` нельзя превращать в 1 через `||`. Unsupported fields не отправляются молча. Добавления совместимы со старым consumer; breaking change — expand/contract с отдельными версиями.
- [ ] **E09.3 — контроль бизнес-настроек.** Модели, цены, availability, categories, шаблоны и лимиты управляются существующим authenticated admin/control plane с audit. Отсутствующее поле не заменять ручным SQL/константой на frontend. Новую конфигурацию вводить только при реальной потребности, с defaults/migration/rollback и серверной авторизацией.
- [ ] **E09.4 — frontend-to-provider трассировка.** Согласовать request/task/draft/transaction correlation через UI→API→validator→queue→adapter→webhook→persistence→delivery. Классификация ошибок различает input/transport/provider/persistence/delivery. У пользователя безопасный support code, у оператора достаточная причина без секрета или промпта.
- [ ] **E09.5 — проверяемая матрица совместимости.** Каждая активная capability имеет UI control и payload/validation path. Contract tests обнаруживают несогласованные mode, required refs, source duration, quality and price tables. Реальная provider документация проверяется перед изменением адаптера; нельзя исправить несовпадение снятием проверок.
- [ ] **E09.6 — метрики и alert policy.** Воронка editor→inputs→quote→submit→accepted→ready→delivered, latency по этапам и процент recoveries. Считать повторные события идемпотентно; не смешивать user abandon с upstream failure. Порог/окно оповещения — утверждённая управляемая настройка. Автомониторинг не включать без отдельного запроса пользователя.

## Приёмка
- [ ] Нет параллельного frontend-прайса и захардкоженных новых provider/model IDs.
- [ ] Zero/missing/invalid capabilities обрабатываются явно и проверяются тестами.
- [ ] Все активные сценарии имеют путь от controls до adapter.
- [ ] Секреты, initData, скрытые промпты и подписанные private URLs не попадают в bundle/analytics/logs.
- [ ] Администратор может менять предусмотренные бизнес-настройки без редеплоя.
- [ ] Сбой конкретной задачи локализуется по correlation ID без чтения чужих данных.
- [ ] Общие правила не расходятся у site/mini_app/telegram_bot.

## Проверки
DTO contract tests с null/zero/unknown поля; schema version skew; admin authorization; feature-disabled response; audit записей; payload round-trip; pricing consistent snapshot; out-of-order updates. CI на exact SHA проверяет backend-quality/webapp/provider-contracts/bot-navigation. Инвентаризационный тест не заменяет реальный пользовательский E2E; он дополнительный барьер.

## Реализация и выпуск
Предпочитать существующий модульный монолит/API client/registry, не создавать новый микросервис для metadata. Внутренний refactor проводить сначала как expand, затем потребители, затем удаление старого, сохраняя зелёные проверяемые срезы. Перед merge фиксировать миграции, обратную совместимость, конфигурационные изменения и риск отката. Закрытие эпика требует evidence по всем активным направлениям, а не одного нового enum.

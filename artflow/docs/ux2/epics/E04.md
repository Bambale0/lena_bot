# [UX2-E04] Запуск, ожидание, восстановление и доставка результата

Source: https://github.com/Bambale0/lena_bot/issues/213

## Цель и зависимости
Программа #209. Пользователь понимает, принят ли запуск, где задача, можно ли закрыть Mini App и как получить готовое. Приоритет P0 для повторных списаний/утраты результата, P1 для остальных состояний. Базовый аудит доступен сразу после #208; привязка draft snapshot зависит от E01 (#210), новый submit UI — E02 (#211).

## Границы
Разделить три состояния: создание задачи, состояние провайдера, доставка результата. `reconciliation_required` не означает ни отказ, ни обычную очередь, ни возврат средств. UI не обходит серверную admission protection. Проценты/ETA показываются только при реальных данных, отмена — только при подтверждённой поддержке.

## Вертикальные срезы
- [ ] **E04.1 — подтверждённый запуск.** До POST фиксируются выбранная модель, параметры, медиа и согласованная цена. Двойной клик, rerender и повторный callback используют одну операцию/idempotency policy. При потере ответа клиент ищет результат исходной операции, а не автоматически отправляет новую платную задачу. Сначала проверить существующие идентификаторы и storage, не создать параллельный источник истины.
- [ ] **E04.2 — карточка активной задачи.** На экране создания и в Работах доступен переход к актуальному статусу. Текст: отправляем/в очереди/создаётся/уточняем/готово/ошибка; неизвестный backend status получает безопасное описание, не raw enum. Видны время старта, прошедшее время и код поддержки. Обновить статус — отдельное read-only действие.
- [ ] **E04.3 — realtime и reconciliation.** WebSocket reconnect с bounded backoff; polling fallback не размножается при смене вкладок. Stale ответ не понижает terminal status, duplicate/out-of-order events дедуплицируются. Resume после сна/офлайна получает актуальную задачу по владельцу. Прерванный fetch не показывается как ошибка генерации.
- [ ] **E04.4 — доставка в Telegram.** Готовый результат доступен в приложении независимо от возможности чата. Отдельно проверить chat permission/write access и отправку. «Доставлено» появляется только после подтверждённого send; иначе понятный CTA открыть/подключить бот. Повторная доставка не запускает генерацию и не списывает ещё раз; message deduplication обязательна.
- [ ] **E04.5 — ошибки с действием.** Invalid input, content rejection, upstream outage, timeout, unknown admission, expired media, download failure различаются. Повтор загрузки, проверка статуса, исправление данных и новый платный запуск не называются одной кнопкой «Повторить». Финансовый текст берётся из ledger/settlement, не из локального предположения.
- [ ] **E04.6 — несколько результатов/частичные запуски.** Пакет имеет список дочерних задач и реальное число принятых. После частичного успеха пользователь видит готовые/ожидающие, не получает сообщение «всё не удалось». Повторяется только явно выбранная незапущенная часть; uncertain child нельзя переотправлять вслепую.

## Приёмка
- [ ] У каждой принятой задачи стабильный идентификатор и путь восстановления после reload.
- [ ] Не более одного списания на логическую операцию; unknown response не делает второй POST.
- [ ] Готовая работа видна без Telegram-чата; доставка отражена отдельно.
- [ ] Нельзя получить чужую задачу по ID или чужой receipt.
- [ ] Никаких фиктивных процентов, возвратов, отмены или сроков.
- [ ] Нет дублирующихся таймеров/сокетов после десятков переключений.
- [ ] Каждая ошибка предлагает допустимое действие без потери draft.

## Проверки
Domain/API: concurrent submissions, duplicate idempotency key, request timeout after admission, out-of-order webhook, duplicate delivery, stale completed→pending, unauthorized task lookup, partial batch failure. Browser: offline/reconnect, close/reopen, low balance, hidden app, missing chat, inaccessible media, stale socket. Исходный сценарий проверять по request_id→task_id→provider_id→ledger→delivery_id, а не только зелёному CI.

## Observability и выпуск
Минимальные поля: actor scope, task/request ID, model/provider, stage, duration, retries, result/delivery outcome. Метрики не публикуют prompts/media URLs. Алерты/таймауты управляемы существующим control plane. Если нужны schema changes — отдельный expand/contract PR с совместимостью и reconciliation. Admin preview не отменяет backend parity для сайта/бота. При регрессии денег остановить новые запуски затронутого маршрута штатным механизмом, а не вручную править balances.

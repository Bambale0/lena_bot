# [UX2] Программа редизайна Mini App: эпики, последовательность и доказательства выпуска

Source: https://github.com/Bambale0/lena_bot/issues/209

## Цель
Довести утверждённый UX/UI 2.0 Telegram Mini App APIX от админского предпросмотра до понятного, безопасного и проверенного продукта. Пользователь выбирает действие, видит материалы и цену, контролирует запуск и находит результат без помощи разработчика.

## Подтверждённая база
PR #208 выпущен: `d97184f4a9587a8237df6504de1fe58ff8142c22`. Есть пять разделов в admin opt-in preview, экран создания, библиотека работ и session-черновики. Это фундамент, а не завершённый редизайн. Источник предыдущих доказательств: #208, комментарий 6087220264.

## Границы
Перерабатываем только Mini App. Не делаем лендинг, не меняем визуал отдельного сайта и текстового бота. Общие API, права, тарифы и финансовые правила сохраняют совместимость. Без новых выдуманных моделей, подписки PRO, процентов генерации, обещанного ETA или неподтверждённых кнопок отмены. Скрытые промпты и встроенные авторские материалы не отправляются клиенту.

## Порядок исполнения и статусы
Одновременно в работе один проверяемый вертикальный срез. Порядок: E01 материалы → E02 редактор → E03 повторы → E04 жизненный цикл → E05 результаты → E06 навигация и поиск → E07 баланс/профиль → E08 WebView/доступность → E09 контроль возможностей и диагностика → E10 пилот. Это порядок выполнения, а не искусственная зависимость всех эпиков друг от друга. Точные блокирующие результаты указаны в каждом эпике; подготовка E08/E09 допускается раньше, но не расширяет текущий scope.

Статусы: `backlog → ready → in_progress → verification → pilot_verified → released`. Закрытие PR не закрывает родительский эпик, пока не пройдены все критерии эпика. Открытый deployment или наличие мок-тестов не считается production verification. Пропущенные проверки указываются явно.

## Обязательный контракт каждого среза
1. Уточнить актуальный SHA и инструкции; сверить существующие API/схемы/тесты и риск соседних изменений.
2. Зафиксировать пользовательское поведение и acceptance tests, воспроизвести RED.
3. Сделать минимальную реализацию; не стирать введённое, не отправлять лишние данные, не ослаблять авторизацию.
4. Проверить unit/контракты/браузер, негативные случаи, reload/back/ошибки сети. Приложить команды и результаты, screenshots для UI.
5. Review: требования, безопасность, конфигурация, telemetry, влияние на сайт/бот.
6. PR → необходимые checks на точный SHA → штатный автодеплой → health, asset SHA и стартовые логи. Никаких push в main или manual checkout production.
7. Обновить активную задачу, эпик и execution ledger. Только затем перейти к следующему срезу.

## Шаблон доказательства
`task_id / base_sha / head_sha / PR / RED / GREEN / screenshots / API-contract checks / admin-preview status / deployment_sha / health / not_verified / rollback`.

## Релизные ограничения
Сохраняем существующий admin opt-in до отдельного прохождения E10. Проверка readonly production не даёт права на платные пробные запросы, массовые рассылки, изменения балансов или разрушительные миграции. Для реальных оплат и генераций сначала ограниченный явный тестовый бюджет и подтверждённый сценарий.

## Успех программы
Все три пути работают: идея → генерация; пример → повтор; задача → результат. Нет потери материалов и повторных списаний; пользователь понимает обязательные входы, стоимость, статус и следующий шаг. Сравнение удобства проводится с измеренным baseline на пользовательских тестах, а не с обещанием роста конверсии.

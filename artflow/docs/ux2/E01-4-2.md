# E01.4.2 — Owner-bound media identity and safe link renewal: contract

**State:** ADR/spec stage, not a deployed feature.
**Issue:** #232; blocked by verified E01.4.1 #229; parent #226 remains open.
**Baseline:** `ef9b7ac4036dc6f649c333a9a8d6fb78d60cc01b`.
**Decision document:** [ADR-UX2-001](../adr/ADR-UX2-001-owned-media.md).

## Problem Statement

A Mini App photo already stored in the user's draft may have disappeared or its URL may be temporary, and the UI cannot prove ownership of that URL. Re-uploading every image is frustrating. Conversely, allowing renewal from arbitrary URLs or local draft IDs would let users claim other people's media. The existing admin-only E01.4.1 checker intentionally distinguishes local existence and external unknown but does not resolve owner identity.

## Solution (for later implementation)

Issue **opaque, durable, user-owned media identities** at authenticated upload time. A server-side lookup/resolve service checks ownership, state and object existence before returning a short-lived access URL. Renewing a link preserves local draft order, material ID, `included` state and prompt. Legacy URL-only drafts stay unowned and can be re-uploaded, not assigned an owner from a hash or URL.

This issue delivers the **approved contract and verifiable test design only**; the next tickets implement it behind safe defaults.

## User Stories

1. As an uploader, I can reopen my own draft and identify the same photo even if its public URL changes.
2. As an uploader, I see whether my own photo is available, temporarily inaccessible, missing or permanently deleted.
3. As an uploader, I can renew a link to an existing *owned* image without paying for or starting generation.
4. As an uploader, I can retry a temporary error without losing the prompt, selection, original order or other photos.
5. As an uploader, I can exclude an unavailable photo and generate from the other verified included files.
6. As an uploader, I must explicitly choose a new source when the underlying file was physically deleted.
7. As an uploader, I do not get a fake "restored" result if the file has been revoked.
8. As an uploader, I can use my own files on another device after authenticating as the same account (when the durable sync UI is added).
9. As a user, I cannot discover or renew another account's private media by guessing its UUID.
10. As a user, I cannot gain ownership by uploading identical bytes, supplying someone else's URL or holding an expired receipt.
11. As a trend remixer, I cannot claim a trend author's hidden references as my own assets.
12. As a user of the existing bot/site, previously submitted tasks, payment operations and public links continue to work during migration.
13. As an operator, I can revoke new-media access and later reconcile deleted bytes without terminating in-flight vendor uploads.
14. As an operator, I can observe failures and retries by IDs and reason codes without logging secrets, raw URLs or content.
15. As a maintainer, I can disable the new feature without destroying rows, breaking legacy clients or changing production schema in an emergency.
16. As a maintainer, I can distinguish signed-link expiry from physical deletion, auth failure, stale revision and provider fetch timeout.
17. As a maintainer, I can safely rotate a dedicated signing key without invalidating unrelated Telegram or webhook credentials.
18. As a developer, I can demonstrate cross-tenant isolation through backend/DB tests rather than relying on disabled frontend buttons.

## Implementation Decisions

- Primary truth: proposed `media_assets` owner/state table; see the ADR for proposed fields and state machine.
- Existing `Generation.user_id` can establish lineage **only for a verified own result**; historical input reference strings and image-session file IDs cannot.
- Existing 24-hour `apixasset` HMAC token is a bounded upload receipt for Trends/Pinterest; it is **not** a durable asset ID. Current flows remain unchanged.
- New logical uploads use random physical keys to avoid cross-user content-hash deletion collisions; dedup is a later storage-layer concern.
- Future ordinary upload API is additive (old URL fields remain); capability disabled until independent migration/review.
- Lookup cannot return internal storage key. Resolve/refresh re-authenticates and emits a purpose-scoped, finite access link only for an authorized current asset.
- Revision-checked and idempotent requests prevent old replies from changing active draft state, issuing grants after revocation or causing duplicate operations.
- No rights inferred from a URL, local reference ID, signature query, hash, filename or unverified generation history.
- Legacy URL-only drafts remain URL-only; optional own-generation adoption requires explicit server-proven lineage.
- Unknown third-party URLs must not be SSRF-fetched. External imports need a separate importer/security contract.
- New private media must not inherit the legacy public immutable CDN path or caching policy.
- Retention, signing key, TTL, limits and controlled rollout must be configured through typed and audited server settings; secrets are kept outside ordinary admin settings.
- No schema, provider, payments, bot, CDN or production data changes in this contract-only step.

## State machine (proposed)

`pending` (allocated but not acknowledged) → `ready` (bytes committed, owner authenticated).
`ready` → `missing` (expected bytes absent) / `revoked` (owner or policy revoked) / `deletion_pending` (authorized cleanup scheduled).
`deletion_pending` → `deleted` when safe and verified; tombstone retained for audit.
`unknown` / `temporary_error` / `refreshable` are **resolution outcomes**, not ways to infer owner or silently restore terminal asset rows.
No automatic transition from revoked/deleted to ready; re-upload creates a new object and ID. A missing file reappearing at the verified same location may be revalidated under an audited owner/revision check, never treated as a new entitlement.

## Auth and authorization rule

For each endpoint, resolve the authenticated actor on the server, require `asset.owner_user_id == actor.id` (or a future separately audited ACL), check active object state, and check revision/operation intent. On unknown or cross-owner asset respond 404 consistently; do not leak object existence in public messages. Ban status, suspended owners and privilege scope must use existing rules. Admin-only preview access and share/public-trend flags must not grant ownership.

## Future contract endpoints (proposed, not deployed)

- `POST /api/web/upload-media` stays compatible; may append `data.asset.id` and `revision` after dual-write.
- `GET /api/web/media-assets/{asset_id}`: current authorized metadata, no raw link/storage key.
- `POST /api/web/media-assets/{asset_id}/resolve`: authorized, versioned request with purpose and request ID; returns availability or a finite new access link.
- A separate owner-authorized revoke/delete operation is part of a later lifecycle ticket, not added in this issue.

The exact HTTP serializers, status codes and idempotency semantics are in ADR section 5; route names remain **proposals** until a later implementation PR.

## Migration/operational gates

1. Architectural review and PR merge of this ADR/spec.
2. Independent additive Alembic implementation ticket, reviewed DB FK/index/constraint shape, test on populated snapshot; migration approval before production.
3. Controlled new upload+registry handshake, failure reconciliation, no hardcoded TTL/key.
4. Owner-scoped read/renew API with authorization/idempotency.
5. Mini App draft migration and real WebView QA, legacy fallback until all writers/readers compatible.
6. Provider ingestion lease and private URL delivery pilot. Validate timeouts/Cloudflare cache behavior, then observe metrics and rollback.
7. Only then consider old-URL deprecation or private-only migration. Destructive cleanup is a separate authorized operation.

## Out of scope

Actual token renewal, DB migrations, mass backfill, CDN policy change, external network fetching, silent asset adoption, provider routing/credits changes, moving old public media, Telegram bot UX changes, enablement for normal users, WebView live checks and paid tests.

## Parity note

`site`: no UI changes; existing media URLs remain valid.
`mini_app`: ADR only, no changed UX in this step.
`telegram_bot`: no changes; future API must preserve equivalent authenticated ownership and existing provider upload flows.
